## 本轮新增（grill-me 二次分析：上游同步影响 / 触发保障 / 免费在线验证）

### 决策
- **清理上游 workflow**：移除全部上游 workflow（master-auto-deploy / nightly-e2e / pr-e2e-mvp / auto-close-old-issues / copilot-issue-auto-comment）及孤立 `.github/scripts/`；仅保留自建 ci / build-base / release + ISSUE_TEMPLATE。原因：这些上游 workflow 在 fork 上会自触发——master-auto-deploy 因缺 `KK_DEPLOY_*` secret 必然失败变红，nightly-e2e 每日定时跑，污染 Actions 状态、误导 CI 判断。
- **免费在线验证（纯 GitHub 原生）**：在 `release.yml`「推送镜像」之后、「创建 Release」之前新增冒烟步骤——`docker pull` GHCR 上刚发布的 `:<版本>` 真实镜像，`docker run -d -p 8012:8012`，轮询 `curl /` 断言 200（最多 ~240s）并查日志含 `Started` 标志，跑完即 `docker stop` 销毁。仅发版 tag 触发；验证失败则流程变红、不产出绿色 Release。采用「内嵌步骤」而非独立 workflow，避免镜像未推完就开始验的竞态。
- **上游同步影响结论**：`building/`、`deploy/`、`.dockerignore`、三个自建 workflow 均为新增、上游无同名 → 合并不冲突；根 Dockerfile 与 maven.yml 已删、每次同步需「保持删除」；`deploy/*/application.properties` 是 `server/src/main/config/application.properties` 的静态快照，上游改服务端默认配置时不会自动同步（**配置漂移点**，同步后需手动 re-copy）。

### 强化：sandbox 丢失未跟踪文件的坑（本轮实踩，重要）
- `ci.yml` / `build-base.yml` 上一轮仅存在于磁盘、**未真正进入 git 树（untracked）**；本回合 sandbox 在命令开头把 `.github` 重置到 HEAD 时，将 `.github` 目录下的 untracked 文件一并清掉，导致一次提交只剩 `release.yml`。
- **教训**：所有 workflow 必须用 `git add` 真正提交进树；创建草稿 + 暂存 + 提交要在**同一条 Bash 命令内**完成，绝不能依赖磁盘上的 untracked 草稿存活到下一命令。写文件优先用引号定界符 heredoc（`<<'EOF'`）避免 `${...}` 被 shell 展开，或写到未跟踪顶层暂存目录再在同命令内 mv 进 `.github`。

## 本轮新增（GHCR 反馈：清理 :cache tag，统一 base :VERSION 与 :latest）

### 问题
- 用户查看 GHCR Packages 发现 `kkfileview-base` 与 `kkfileview` 均存在公开的 `:cache` tag。
- `kkfileview` 的 `:latest` 与 `:5.0.2` 显示为同一镜像（符合期望），但 `kkfileview-base` 中二者分开显示。

### 根因
- workflow 使用了 `--cache-to type=registry,ref=...:cache,mode=max`，buildx 会把缓存以独立 tag `:cache` 推送到 GHCR。

### 修复
- 全部改为 `--cache-to type=inline`：缓存内嵌在 `:latest` 镜像 manifest 中，不再产生额外的 `:cache` tag。
- `--cache-from` 改为从 `:latest` 读取（inline cache 可被 `type=registry,ref=...:latest` 识别复用）。
- `release.yml` 中基础镜像复用步骤：`imagetools create` 同时打 `--tag :<VERSION>` 和 `--tag :latest`，确保二者在 GHCR 中显示为同一镜像、同一时间戳。
- 涉及文件：`build-base.yml`、`release.yml`。

### 影响
- 已存在的 `:cache` tag 不会自动删除，只是未来不再生成；需用户手动在 GHCR UI 删除历史 `:cache` tag。
- `v5.0.2` tag 已移动到修复后的 HEAD（86b52547）。

## Round 8 (15:19) — 禁用 BuildKit provenance，清理 GHCR 里的 unknown/unknown
- 现象：用户在 GHCR Package 页面看到 `kkfileview-base:5.0.2` 的 OS/Arch 除了 `linux/amd64`、`linux/arm64`，还有一条 `unknown/unknown`。
- 诊断：`unknown/unknown` 是 Docker Buildx/BuildKit ≥0.11 对多平台构建默认生成的 **SLSA provenance attestation** 附加 manifest，记录构建来源信息，不是可运行镜像；`docker pull` 正常架构时会自动忽略它。
- 修复：在三个 `docker buildx build --push` 命令上加 `--provenance=false`，分别位于 `build-base.yml` 的基础镜像构建、`release.yml` 的基础镜像回退构建、`release.yml` 的最终镜像构建。另在注释里说明原因。
- 影响：已发布的旧 tag 里仍保留 `unknown/unknown`（不会自动消失），未来重新构建的镜像不再生成该条目。
- 提交：52bde07a。
- 可复用教训：用 Buildx 推多架构镜像到 GHCR 时，若不想出现 `unknown/unknown`，统一加 `--provenance=false`；需要 SLSA 来源证明时再打开。
