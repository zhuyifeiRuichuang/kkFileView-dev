## kkFileView-dev：CI/CD 与部署改造（grill-me 设计后落地）

对 kekingcn/kkFileView 的 fork（origin: zhuyifeiRuichuang/kkFileView-dev，版本 5.0.2）完成三项改造，已本地提交 + 移动 v5.0.2 tag 到 master HEAD，但**推送需用户本机 GitHub 鉴权**（沙箱无写凭证）。

### 决策（grill-me 锁定）
1. 触发：推送 `vX.Y.Z` tag 触发全量发布；master 仅 CI 校验；版本号从 tag 去 v 解析。
2. Release 产物：Linux tar.gz 发行包 + 独立可运行 jar。
3. 镜像：GHCR（`ghcr.io/zhuyifeiruichuang/kkfileview-base` 与 `kkfileview`），amd64+arm64 多架构。
4. 去重：building/base 路径过滤重建 :latest；发版用 `docker buildx imagetools create` 把 :latest 别名 :版本（零层重推）；布局 `building/base` + `building/final`，删根 Dockerfile。
5. 部署：deploy/docker(docker-compose 卷挂载) + deploy/k8s(Deployment+ClusterIP+NodePort+ConfigMap)；版本无关软链 /opt/kkfileview。

### 关键坑
- GitHub owner `zhuyifeiRuichuang` 含大写，GHCR 必须小写 `zhuyifeiruichuang`（workflow 用 `${GITHUB_REPOSITORY_OWNER,,}` 小写化）。
- 上游已存在 annotated tag `v5.0.2`（指向 c4288f7e），本地已 `git tag -f` 移动到 master HEAD(57038e00)，否则 Release 会从旧提交构建、漏掉 CI/部署改动。origin 上无此 tag，推送即创建。
- 沙箱 Bash 会重置受版本控制的目录（如 .github）到 HEAD，导致其中未提交文件丢失；需用 Write 写文件 + 同一条 Bash 命令内 mkdir/git add/commit，或暂存到未跟踪顶层目录。
- arm64 下 LibreOffice 安装极慢，基础镜像构建时长会很长（已用 registry 缓存缓解）。
